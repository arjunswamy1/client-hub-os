- Slack DMs go only through `postDirectMessage()` in `_shared/slack-post.ts` (user ids only, internal team members only); channel posts only through `postToSlack()`. Why: DMs cannot enter the channel allowlist without weakening it.
- Brief accept/decline are the single `accept_creative_brief_as` / `decline_creative_brief_as` SQL functions (decline never changes status or assignee; lead from `team_members.is_creative_lead`); brief notifications are queued in the database before any Slack call, deduped on `dedupe_key`. Why: one atomic path and exactly-once notifications.

- The MCP server is authored only in `src/lib/mcp/` (tools query via `supabaseForUser`, OAuth via Supabase); `supabase/functions/mcp` is generated by the Vite plugin. Why: RLS runs as the connecting user and the generated file is overwritten each build.
- New-business knowledge extraction validates in `_shared/nb-knowledge.ts` (verbatim evidence, proof points need a figure in the evidence) and always inserts `internal_only`; clearance happens only in the hub. Why: client economics must never leave CPM without a named person approving it.
- Period comparisons (same weekday / prior day / prior week) live only in `_shared/metric-comparisons.ts` (pure rules) and `_shared/metric-comparison-data.ts` (snapshots via `computeClientMetrics`); the drafter and the CPM bot both call `buildComparisonSet()`. Why: one comparison path; absent is not zero.
- `metric_revision_log` is written only by `_shared/metric-revision-log.ts`, insert-only, called after each spend sync's upsert; a trigger refuses UPDATE/DELETE. Why: provisionality must be detected from observed revisions, not assumed.
- Meta campaign rows in `ad_campaigns` are keyed by `platform_campaign_id` (name is only the latest label); the sync replaces legacy name-keyed rows for days it re-pulls. Why: renames created duplicate spend rows.
- Agents reach the hub only through `supabase/functions/mcp-hub`, authenticated either by hashed `agent_tokens` or by a hub OAuth sign-in (token must carry an OAuth `client_id` claim and map to an active internal `team_members` row); client access derives from `client_assignments`/admin, every call lands in `agent_query_log` with its auth method; reads go through the canonical engine and `_shared/data-health.ts`, and it must never import `_shared/slack-post.ts`. Why: agents get vetted figures with provenance, act as a named person, and are structurally unable to send.
- Jacuzzi lead files arrive by email and are synced only by `supabase/functions/jacuzzi-lead-email-sync` (pure parsing and sheet row math in `_shared/jacuzzi-lead-sheet.ts`; each Gmail message processed once via `jacuzzi_lead_email_log`; inserts new leads only, prices from `jacuzzi_payout_rates`). Why: one idempotent path from email to hub to client sheet.
- Service identities are `team_members` rows with `is_service_account = true`: client access is all active clients, they are refused as assignees by a database trigger, and every picker, digest and DM lookup filters them out. Why: an agent must never receive work, messages or capacity.
- Channel posts from hub jobs go out through `postToSlack()`; when `bot_runtime_settings.outbound_sender = 'grokbot'` a cleared post is written to `slack_outbox` instead, and Grokbot sends it via the mcp-hub outbox tools (service accounts only, channel re-checked at read). `cpm_bot_replies` gates CPM Bot's answers. Why: Grokbot replaces CPM Bot without moving the external-channel allowlist out of the hub.
- Grokbot and CPM Bot share one bot implementation in `_shared/slack-bot-app.ts`; `supabase/functions/grokbot` sets the persona (`_shared/bot-persona.ts`) so the token, signing secret and outbox bypass switch to Grokbot's, and a `slack_outbox` insert trigger wakes it to drain via mcp-hub. Why: one answering brain and one Slack write gate, two Slack identities.
- Tasks are created only by `_shared/task-request.ts` (`createRequestedTask`), from an @CPM Bot Slack request (`slack-bot-app.ts`) or an explicit spoken request in a recording (`extract-meeting-tasks`); detection rules live only in `_shared/task-request-rules.ts`, dedupe on `type_data.source_ref`. Candidate promotion, Fathom action items, Slack client-request scanning and Henry intake are switched off (`TASKS_FROM_REQUESTS_ONLY`). Why: the tracker holds only work someone deliberately asked to track.
- Creative chasing (follow-up ladder, daily cap, weekend rule, check-in parsing) lives only in `_shared/creative-followups.ts`; `supabase/functions/creative-followups` is the only sender, and `creative_followups` is unique on (brief, rule, stage). Why: each chase fires exactly once, and only active briefs are ever in scope.
- Daily-update context rules (strict internal-channel test, origin split, figure check, narrative fallback, discovery) live only in `_shared/update-context.ts`; daily updates post only via `postToSlack({ internalOnly: true })`. Why: no update reaches a shared channel and no agent figure goes unchecked.
- Some subdirectories have their own AGENTS.md; read it before changing files there.
